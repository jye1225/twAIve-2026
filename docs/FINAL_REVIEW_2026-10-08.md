## 결론

새 기능이나 전체 디자인 개편보다 계정 전환, 기록 초기화, 저장 실패, 늦게 도착하는 AI 응답을 먼저 수정해야 한다. 현재 상태를 오류 없는 공개 청소년 서비스로 설명하는 것은 적절하지 않다. 재심사에서는 교육용 프로토타입, 정책 기반 루브릭, 아직 검증이 필요한 부분을 분리해 설명한다.

최초 점검 단계에서는 운영 소스를 수정하거나 재배포하지 않았다. 이후 수정 작업은 별도 결과 문서에 기록했다. 실제 사용자의 기록을 삭제하거나 덮어쓰는 재현은 하지 않았으며, 아래 오류 재현은 격리된 가짜 계정·저장소를 사용했다.

### 1. 계정 전환 재현

계정 A의 딥페이크 선택 4개가 메모리에 있는 상태에서 로그아웃하고 저장 기록이 전혀 없는 계정 B로 로그인했다. `state.progress`는 비었지만 `state.history`와 `state.assessments`는 남아, B의 기록 탭과 종합 분석에 A의 선택 4개가 포함됐다.

이는 서버의 RLS를 우회해 다른 계정의 DB를 읽은 문제가 아니라 브라우저 메모리의 계정 간 분리가 안 된 문제다. 학교 공용 기기에서는 특히 중요하다. 이후 저장 경로가 이 상태를 사용하면 잘못된 기록을 B에게 저장할 위험도 있다. 이전 계정의 저장 요청이 늦게 완료되는 경우까지 막아야 한다.

검증 기준: A→로그아웃→빈 B의 기록·점수·프로필 분석은 비어 있어야 한다. B에서 첫 플레이를 시작하면 A의 사전·사후 응답 및 회차가 섞이면 안 된다. 늦게 완료된 A 요청도 B 화면에 영향을 주면 안 된다.

### 2. 초기화 버튼 재현

완료된 기록을 저장한 뒤 기록 탭에서 상단 ‘처음으로’를 눌렀다. 실제 이벤트 처리기는 `startEpisode(..., {loadSaved:false, saveReset:true})`를 실행했고, 같은 사용자·에피소드 행을 `completed:false`, `history:[]`로 upsert했다. 결과리포트 접근 조건도 사라진다. 현재 DB는 사용자·에피소드당 최신 행 하나를 저장한다.

새 플레이의 기존 기록 대체 정책과 홈 이동을 혼동하면 안 된다. ‘다시 플레이’에도 기존 최신 결과를 대체한다는 확인이 필요하며, 회차별 결과 보관은 이번 재심사 후 별도 기능으로 두어도 된다.

검증 기준: 기록·학습·마이페이지·리포트 어디에서 상단 버튼을 눌러도 DB 쓰기가 발생하지 않아야 한다. 새 플레이 취소 시 기존 리포트는 그대로 남아야 한다.

### 3. 저장 실패 재현

최종 사후 응답 저장을 오류로 돌려보냈다. 앱은 이미 결과 모드로 전환됐으며, 저장 함수의 false 반환값을 확인하지 않았다. 결과 렌더러는 실제 성공 여부와 무관하게 ‘선택 기록과 사전·사후 응답이 저장되었습니다.’를 표시한다. 이 문구가 CSS로 숨겨지는 화면에서도 명확한 저장 실패·재시도 안내가 없다는 문제는 남는다.

검증 기준: 연결 실패 때 결과를 계속 읽을 수 있더라도 ‘아직 저장되지 않았어’와 재시도를 제공해야 한다. 재시도 후 새로고침·재로그인했을 때 동일한 결과가 복원돼야 한다.

### 4. AI 응답 혼선 재현

에피소드 A의 AI 요청을 대기시킨 후 다른 리포트의 출력 영역과 97점 상태로 바꿨다. A 응답을 반환하자 실제 렌더러는 새 출력 영역에 A의 딥페이크 설명과 현재 97점 결과를 같이 넣었다. 요청 함수는 응답 시 에피소드나 세션을 확인하지 않고 현재 DOM을 찾는다.

AI 설명 요청에는 클라이언트 제한 시간도 없다. 이유 추천은 10초 제한이 있으나, 결과 설명은 별도의 취소·시간 초과·재시도 경로를 추가하는 것이 좋다.

검증 기준: AI 요청 후 기록 탭에서 다른 에피소드 리포트로 이동해도 이전 답변이 붙지 않아야 한다. 로그아웃·재로그인, 같은 탭을 다시 여는 경우도 포함한다.

## 청소년 대상 콘텐츠와 운영

### P2: 기본 판단 이유가 위험한 행동을 합리화할 수 있음

`js/app.js:2904`의 기본 이유는 어떤 선택이든 첫 항목을 ‘당사자한테 가장 덜 피해를 줄 것 같아서’로 만든다. ‘그냥 모른 척 지나간다’ 같은 선택에도 이 문구가 나오는 것을 재현했다. AI가 실패할 때 제공하는 이유 3개가 실제 마음과 맞지 않으면 학생은 부정확한 이유를 강제로 고르게 된다.

권장: 행동을 옳다고 보증하지 않는 중립적인 이유를 제공하고 ‘맞는 이유가 없어/잘 모르겠어’를 포함한다. AI가 제시한 이유를 선택한 데이터는 학생의 생각을 직접 측정한 자유 응답과 구분한다. 현재 행동 점수 자체는 이 이유 문구가 아닌 루브릭으로 계산한다.

### 공개 운영 전 필수: 개인정보처리방침과 연령 절차

`index.html:25`의 회원가입에는 이름·아이디·비밀번호가 있지만 연령 확인이나 동의 절차가 없다. `privacy.html:27`, `78`, `88`, `97`에는 운영자, 문의처, 저장 지역, 보유·삭제 절차, 만 14세 미만 절차가 미정으로 남아 있다. 단순히 동의 체크박스만 추가해서 해결되는 문제는 아니다.

오늘 밤 현실적인 범위: 재심사는 성인 심사자용 전용 테스트 계정과 가상 기록으로 진행한다. 실제 학생 공개 모집은 운영 정책이 확정될 때까지 보류한다. 표시 이름은 실명 대신 별명을 사용하도록 바꾸는 편이 데이터 최소화에 유리하다. 운영자·삭제 연락처 등은 담당자가 실제 정보를 결정해야 하며 임의로 채우면 안 된다.

개인정보 보호법 제22조의2는 만 14세 미만 아동의 개인정보 처리에 법상 동의를 받아야 하는 경우 법정대리인 동의와 확인을 요구한다. 적용 범위와 실제 절차는 별도 검토가 필요하다. [국가법령정보센터](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1020398523).

### 공개 운영 전 필수: 자유 질문의 개인정보와 안전

`api/explain-result.js:86`은 자유 질문을 길이·공백만 정리해 모델 입력에 포함한다. 계정 이름과 아이디 필드를 제외한 것은 좋지만, 질문에 직접 적은 친구 이름·학교·상담 내용은 그대로 전송될 수 있다. `js/app.js:2113`의 ‘이름과 아이디는 AI에게 보내지 않아’는 이 예외를 충분히 설명하지 못한다.

권장: 재심사 전에는 질문을 결과에 관한 추천 질문으로 제한하거나, 적어도 개인정보 입력 금지 안내를 분명히 한다. 실제 공개 운영에는 개인정보 처리 설계, 연령에 맞는 안전 필터, 위기 상황에서 사람에게 도움을 연결하는 경로, 신고 기능을 추가한다. 정신건강 에피소드는 친구가 혼자 책임져야 한다는 인상을 피해야 한다. 현재 프롬프트에 상담교사·믿을 만한 어른 연결 지시가 있는 점은 긍정적이지만, 프롬프트만으로 고위험 대응이 보장되지는 않는다.

OpenAI의 미성년자 가이드는 연령에 맞는 안내·안전 필터·고위험 상호작용 대응 등을 요구하며, 13세 미만 또는 적용되는 디지털 동의 연령 미만의 개인정보 처리에는 Zero Data Retention 조건을 명시한다. `store:false`만으로 ZDR 적용 여부가 입증되지는 않는다. 실제 계정의 ZDR 설정은 이번 점검에서 확인하지 않았다. [OpenAI 미성년자 가이드](https://developers.openai.com/api/docs/guides/safety-checks/under-18-api-guidance), [데이터 관리 안내](https://developers.openai.com/api/docs/guides/your-data).

### 공개 운영 전: 외부 영상과 API 사용량

`api/explain-result.js:503`은 YouTube 검색에 safeSearch strict를 사용하지만 교육 자료의 신뢰성·연령 적합성을 보증하지 않는다. API 키가 없거나 검색이 실패하면 제공하는 일반 검색 링크에는 같은 필터 조건도 없다. 가능하면 교사가 검토한 영상 목록을 우선한다.

로그인 검증은 있으나 서버 코드에는 사용자별 AI 요청 한도나 예산 제한이 없다. 버튼 비활성화는 반복 API 호출을 막는 서버 보호가 아니다. 공개 이용 전 사용자별 한도, 서버 제한 시간, 비용 알림을 설정한다.

## 디자인·표현에서 권장할 수정

- ‘Bad End’나 ‘AI 의존 점검형’을 아이의 고정된 정체성으로 보이게 하지 않는다. ‘이번 선택에서 더 연습할 점’처럼 현재 기록에 한정하고 잘한 선택과 다음 행동을 함께 제시한다.
- `js/app.js:1964`의 ‘데이터 신뢰도 XX%’는 실제 분류 정확도가 아니다. `js/analysis/learner-classifier.js:33`에서 기록 수·이유 응답률·사전사후 유무·회차를 합성한 지표다. ‘분석에 사용한 기록의 충분도’ 등으로 이름을 바꾸고 정확도·통계적 확률로 설명하지 않는다.
- 로고 PNG는 약 2.04MB, 에피소드 이미지는 각각 약 2.29~2.68MB다. 첫 인트로 이미지와 로고만 약 4.72MB여서 느린 모바일 환경에서 기다림이 길 수 있다. 시연은 미리 이미지 로드를 확인하고, 배포 최적화는 WebP 등으로 별도 진행한다.
- 최신 로그인 제목은 26px, 라벨은 14px의 밝은 색이며 GmarketSans가 지정돼 있다. 현재 확인한 620px 브라우저에서는 가로 넘침이 없었다. CSS에서 금지한 `#405b7c`, `#6c7e94`는 검색되지 않았다.
- 입력창 14px는 iOS에서 포커스 확대 여부를 실제 기기로 확인할 필요가 있다. 키보드가 열린 상태, 가로 모드, 글자 확대, 작은 터치 영역도 별도 확인한다. 이번 점검은 실제 iOS 검증을 하지 않았다.
- 새로 배포해도 이미 열린 탭의 자바스크립트는 이전 코드다. 점검 시작 시 열린 탭은 앱 v20261008-2·CSS v20261008-3을 유지해 상세 분석이 새 창으로 열렸다. 새로고침 후 v20261008-5 로드가 확인됐다. 시연 전에 반드시 최신 탭을 준비한다.

## 재심사에서 정확히 설명할 연구 한계

1. 평가 축은 국가 AI 윤리원칙에서 가져왔지만, 선택별 0~4단계 배정과 75/50점 엔딩 경계는 팀이 만든 교육용 조작적 기준이다. ‘정부가 점수를 정해줬다’ 또는 ‘객관성이 완전히 검증됐다’고 설명하지 않는다.
2. 정책 근거를 추적할 수 있게 된 것과 타당성 검증을 완료한 것은 다르다. 전문가 평가, 평가자 간 일치도, 학생 사용성·학습 효과 검증은 후속 과제다.
3. 현재 웹의 학습 유형 분류는 규칙 기반이다. `js/analysis/learner-classifier.js:44`가 위험 선택 비율과 취약 원칙 등의 임계값을 사용한다. OpenAI는 행동 점수를 매기는 주체가 아니라 이유 추천과 결과 해설을 제공한다.
4. K-means는 `ml/cluster_learners.py`의 별도 오프라인 탐색 코드다. 실시간 웹 분류를 K-means 예측 결과라고 설명하면 안 된다. 실제 학습 실행·모델 검증 완료 여부는 별도 산출물로 증명해야 한다.
5. 50건은 내부 파일럿 실행 기준이지 통계적으로 충분한 표본 수라는 보장이 아니다. 현재 `validate_dataset`은 동의한 행 수를 세며 독립 학생 수, 완료·점수 버전, 값 범위까지 검증하지 않는다. CSV 생성 단계와 분석 단계의 조건을 맞춰야 한다.
6. `supabase/schema.sql:180`의 교수자 집계는 구버전 기록을 명시적으로 제외하지 않는다. 구버전 데이터가 남아 있으면 버전 3만 표시하는 학생 화면과 통계가 다를 수 있다. 실제 Supabase에 반영된 SQL 및 데이터 상태는 별도 확인이 필요하다.

## 수정 후 시연 리허설

1. 새로고침한 최신 Chrome 탭에서 전용 테스트 계정으로 로그인한다.
2. 전용 계정으로 에피소드 하나를 사전 질문부터 사후 질문까지 완주한다.
3. 저장 완료를 확인한 뒤 새로고침하고 기록 탭에서 같은 점수와 결과리포트를 복원한다.
4. 상세 분석·AI 설명·학습 이동이 같은 화면에서 이어지는지 확인한다.
5. AI 설명이 생성 응답인지 기본 설명인지 구분해서 확인하고, 끊긴 문장·긴 대기·다른 주제 응답이 없는지 본다.
6. 로그아웃하고 빈 두 번째 테스트 계정으로 로그인해 이전 기록이 안 보이는지 확인한다.
7. 교수자 계정에서 접근 권한, 실제 집계와 합성 시연 데이터 구분, 마이페이지 복귀를 확인한다.
8. 실제 학생 개인정보가 아닌 가상 기록으로 준비한 화면 녹화와 리포트 캡처를 네트워크 장애 대비 자료로 둔다.

수정 우선순위는 1~4번 기능 오류, 중립적 기본 이유, 신뢰도 표현 정리, 실제 로그인·저장·AI 리허설 순서다. 심사 직전에는 루브릭 전체 개편, 새 알고리즘 연결, 전체 CSS 재작성처럼 영향 범위가 큰 변경은 피한다.
