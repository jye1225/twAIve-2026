# twAIve 팀 시스템 공부 교재

> 목적: 팀원 3명이 현재 시스템을 실제로 이해하고, 교수님의 개발 질문에 각자 자기 말로 답할 수 있도록 만든 재심사 준비 자료

## 0. 제일 먼저 합의할 한 문장

twAIve는 **학생이 AI 윤리 상황에서 선택한 행동과 판단 이유를 기록하고, 국가 AI 윤리원칙 기반의 설명 가능한 규칙으로 분석하여 학생 피드백과 교수자용 지도 정보를 제공하는 웹 학습 시스템**이다.

이 프로젝트의 핵심은 단순히 선택지에 점수를 더하는 것이 아니다.

```text
상황 제시
→ 행동 선택
→ 선택 이유와 응답 시간 기록
→ 7대 윤리원칙별 행동 수준 계산
→ 취약 원칙과 학습 패턴 분석
→ 학생 맞춤 피드백·다음 학습 추천
→ 교수자용 익명 집계와 지도 활동 제안
```

# 1. 먼저 알아야 할 아주 기초적인 말

## 1.1 프론트엔드

사용자가 브라우저에서 직접 보는 화면과 상호작용을 말한다.

- 로그인 화면
- 에피소드 목록
- 질문과 선택지
- 결과 리포트
- 마이페이지
- 교수자 대시보드
- 모바일·데스크톱 반응형 화면

twAIve에서는 주로 다음 파일이 프론트엔드다.

- `index.html`: 화면의 기본 뼈대
- `css/styles.css`: 색상, 크기, 배치, 반응형 디자인
- `js/app.js`: 버튼을 눌렀을 때 화면을 바꾸고 데이터를 처리하는 로직

## 1.2 백엔드

브라우저에 그대로 공개하면 안 되는 작업, 데이터 저장, 사용자 인증, 권한 검사를 담당하는 부분이다.

twAIve는 서버 한 대를 직접 운영하지 않고 두 서비스를 조합한다.

- Supabase: 회원 인증, PostgreSQL 데이터베이스, 접근 권한 관리
- Vercel Serverless Function: OpenAI 비밀 키를 숨긴 채 API를 호출하는 서버 함수

## 1.3 데이터베이스

사용자와 학습 기록을 오래 저장하는 표들의 모음이다. 엑셀 파일처럼 행과 열이 있지만, 여러 사용자가 동시에 안전하게 사용하도록 설계된 서버 저장소다.

twAIve의 핵심 표는 다음과 같다.

- `auth.users`: Supabase가 관리하는 로그인 계정과 암호 정보
- `profiles`: 아이디, 이름, 분석 동의 여부
- `user_episode_progress`: 에피소드별 진행 위치, 점수, 선택 기록, 사전·사후 응답
- `teacher_accounts`: 교수자 대시보드를 볼 수 있는 계정 목록

## 1.4 API

서로 다른 프로그램이 정해진 형식으로 요청과 응답을 주고받는 통로다.

예를 들어 브라우저가 서버에 다음처럼 부탁한다.

```text
요청: 이 로그인 토큰이 진짜인지 확인하고, 이 결과를 쉽게 설명해줘.
응답: 요약, 점수 이유, 다음 행동, 추천 영상 검색 결과
```

twAIve가 사용하는 주요 API는 다음과 같다.

- Supabase Auth API: 회원가입, 로그인, 로그아웃, 세션 확인
- Supabase Data API: 프로필과 학습 기록 조회·저장
- Supabase RPC: 아이디 중복 확인, 교수자 통계 집계
- OpenAI Responses API: 결과 설명과 상황별 판단 이유 생성
- YouTube Data API: 학습 영상 검색

## 1.5 JSON

프로그램끼리 데이터를 주고받을 때 쓰는 구조화된 글 형식이다.

```json
{
  "episode_id": "deepfake",
  "score": 74,
  "completed": true
}
```

문장 하나로 저장하는 것보다 `episode_id`, `score`, `completed`처럼 의미가 분리되어 있어서 프로그램이 다시 읽고 분석할 수 있다.

## 1.6 모델이라는 말의 세 가지 뜻

twAIve에서는 아래 세 가지를 절대 섞어 말하면 안 된다.

### A. 현재 실제로 실행되는 자체 분석 모델

- 종류: 설명 가능한 규칙 기반 모델
- 파일: `js/analysis/` 폴더
- 팀이 정한 명시적 계산 규칙으로 작동
- 입력: 원칙별 점수, 선택 이유, 응답 시간, 사전·사후 변화
- 출력: 취약 원칙, 학습자 유형, 데이터 충분도, 다음 콘텐츠

### B. 외부 생성형 AI

- 종류: OpenAI 모델
- 역할: 계산된 결과를 쉬운 말로 설명하고, 상황에 맞는 판단 이유 후보를 생성
- 점수를 결정하지 않음
- 자체 학습한 모델이 아님

### C. 실제 데이터가 충분해진 뒤 사용할 탐색 모델

- 종류: K-means 군집분석
- 파일: `ml/cluster_learners.py`
- 역할: 비슷한 응답 패턴을 가진 학습자 집단 탐색
- 현재 50건 미만이면 실행을 막음
- 정답을 맞히는 분류 모델이 아니라 비슷한 패턴끼리 묶는 비지도학습

발표에서는 이렇게 말하면 가장 정확하다.

> 현재 서비스의 개인 분석은 저희가 구현한 설명 가능한 규칙 기반 모델이 담당합니다. OpenAI는 그 결과를 자연어로 설명하는 보조 기능입니다. 실제 동의 데이터가 파일럿 기준에 도달하면 K-means로 집단 학습 패턴을 탐색하도록 별도의 오프라인 파이프라인도 구현했습니다.

# 2. 전체 시스템을 식당에 비유하기

처음 배우는 사람은 시스템을 식당처럼 생각하면 쉽다.

| 시스템 | 식당 비유 | twAIve 역할 |
|---|---|---|
| 브라우저 | 손님 자리 | 학생과 교수자가 보는 화면 |
| HTML | 가구와 방 구조 | 입력창, 버튼, 콘텐츠 영역 |
| CSS | 인테리어 | 색, 글자, 여백, 반응형 배치 |
| JavaScript | 종업원 | 클릭을 받고 화면과 데이터를 갱신 |
| Supabase Auth | 신분 확인 | 누가 로그인했는지 확인 |
| PostgreSQL | 주문 장부 | 프로필과 학습 기록 저장 |
| RLS | 장부 열쇠 | 본인 기록만 보게 제한 |
| Vercel API | 주방 | 비밀 키가 필요한 작업 수행 |
| OpenAI | 외부 전문 도우미 | 결과를 쉬운 문장으로 설명 |
| 분석 엔진 | 조리법 | 같은 입력에는 같은 계산 결과 제공 |

핵심은 브라우저가 OpenAI 비밀 키를 직접 가지지 않는다는 점이다. 브라우저는 Vercel 서버 함수에 요청하고, 서버 함수가 환경변수에 숨겨진 키로 OpenAI를 호출한다.

# 3. 전체 구조

```text
[학생 브라우저]
  ├─ HTML/CSS로 화면 표시
  ├─ js/app.js로 상태와 사용자 동작 처리
  ├─ js/analysis/*.js로 점수와 개인 학습 분석
  ├─ Supabase Auth로 로그인
  ├─ Supabase DB로 학습 기록 저장
  └─ /api/explain-result로 AI 설명 요청
                         │
                         ▼
              [Vercel Serverless Function]
                ├─ Supabase 토큰 검증
                ├─ 입력값 길이·형식 검증
                ├─ OpenAI Responses API 호출
                ├─ YouTube Data API 호출
                └─ 오류 시 로컬 설명 반환

[교수자 브라우저]
  └─ Supabase RPC get_teacher_dashboard()
       ├─ teacher_accounts 권한 확인
       ├─ 익명 통계만 서버에서 집계
       └─ 이름·아이디·개별 답변은 반환하지 않음

[오프라인 분석]
  └─ 동의한 적격 CSV 50건 이상
       └─ Python + scikit-learn K-means
            └─ 비슷한 학습 패턴과 지도 활동 요약
```

# 4. 로그인부터 결과 저장까지 한 바퀴

## 4.1 처음 사이트를 열었을 때

`index.html`이 로그인 화면과 앱 화면의 기본 구조를 만든다. `css/styles.css`가 디자인을 적용하고, 여러 분석 파일과 `js/app.js`가 순서대로 로드된다.

`js/app.js`의 `loadSession()`은 Supabase에 현재 로그인 세션이 있는지 묻는다.

- 세션이 있으면 프로필, 전체 학습 기록, 교수자 권한을 불러온다.
- 세션이 없으면 로그인 화면을 보여준다.

세션은 “이미 로그인한 사용자인지 증명하는 임시 출입증”이라고 생각하면 된다.

## 4.2 회원가입

학생은 이름, 아이디, 비밀번호를 입력한다.

Supabase Auth는 기본적으로 이메일과 비밀번호 방식이므로, 화면에는 이메일을 받지 않지만 내부적으로 아이디를 다음 형태로 바꾼다.

```text
입력 아이디: minji01
내부 인증 주소: minji01@twaive-user.example.com
```

`usernameToAuthEmail()`이 이 변환을 한다. 이 주소는 로그인 기술을 위한 내부 식별자이며 실제로 메일을 받는 주소가 아니다.

회원가입 순서:

1. 아이디 형식 검사: 영문 소문자, 숫자, 밑줄 3~20자
2. `is_username_available` RPC로 중복 확인
3. 이름과 비밀번호 확인
4. `supabase.auth.signUp()`으로 인증 계정 생성
5. `profiles`에 아이디, 내부 인증 주소, 이름 저장

비밀번호는 `profiles`에 저장하지 않는다. Supabase Auth가 암호화된 인증 시스템 안에서 관리한다.

## 4.3 로그인

1. 사용자가 아이디와 비밀번호를 입력한다.
2. 아이디를 내부 인증 주소로 변환한다.
3. `signInWithPassword()`를 호출한다.
4. 성공하면 Supabase가 사용자 정보와 세션 토큰을 준다.
5. 프로필과 저장된 학습 기록을 불러온다.

## 4.4 에피소드 시작

`startEpisode()`가 다음 상태를 초기화한다.

- 선택한 에피소드 번호
- 시작 장면
- 이번 시도의 선택 기록
- 화면 단계 `pre`
- 시도 횟수

여기서 화면 단계는 일종의 상태 머신이다.

```text
home → pre → story → reason → story ... → post → report
```

- `pre`: 사전 질문
- `story`: 상황과 행동 선택지
- `reason`: 방금 행동을 선택한 이유
- `post`: 사후 질문
- `report`: 결과 리포트

상태 머신을 쓴 이유는 한 HTML 페이지 안에서 현재 단계에 맞는 화면만 안정적으로 표시하기 위해서다.

## 4.5 행동 선택

학생이 선택지를 누르면 `queueChoice()`가 바로 다음 장면으로 넘기지 않고 선택을 임시 보관한다.

기록하는 내용:

- 장면 ID와 제목
- 선택지 번호와 문장
- 선택지 피드백
- 선택지별 윤리 루브릭
- 다음 장면 ID
- 장면을 본 뒤 선택하기까지 걸린 시간

그다음 “왜 이 선택을 했어?” 화면으로 이동한다.

## 4.6 판단 이유 생성

브라우저는 로그인 토큰과 현재 에피소드·장면·선택 문장을 Vercel API에 보낸다. 서버는 OpenAI에 서로 다른 관점의 이유 3개를 JSON 형식으로 요청한다.

허용된 이유 코드는 여섯 가지다.

- `rights`: 권리와 피해
- `verification`: 사실과 출처 확인
- `action`: 신고와 후속 행동
- `convenience`: 편의와 재미
- `social`: 친구 관계와 분위기
- `uncertain`: 판단 기준의 불확실성

AI가 만든 문장을 그대로 믿지 않는다.

- 반드시 3개인지 확인
- 허용 코드인지 확인
- 코드가 서로 다른지 확인
- 10대 반말 형식인지 확인
- 문장 길이를 제한
- 10초가 넘거나 오류가 나면 미리 만든 안전한 3개 이유를 표시
- 같은 장면은 브라우저 세션에서 캐시하여 반복 호출을 줄임

학생이 이유를 고르면 `applyDecisionReason()`이 실제 선택 기록을 완성한다.

## 4.7 점수 갱신

각 선택지에는 장면별로 관련 윤리원칙 수행 수준이 들어 있다.

```json
{
  "privacy": 4,
  "responsibility": 3,
  "transparency": 2
}
```

이 숫자는 다음 행동 루브릭이다.

| 단계 | 뜻 |
|---:|---|
| 0 | 원칙을 직접 위반하거나 피해를 확대 |
| 1 | 위험을 무시하거나 방관 |
| 2 | 문제를 알지만 조치가 부족 |
| 3 | 기준을 확인하고 책임 있게 행동 |
| 4 | 예방·검증·공개·피해 회복까지 적극 실천 |

`refreshGuidelineScores()`가 지금까지의 선택 기록을 다시 읽고 원칙별 점수를 계산한다.

## 4.8 진행 기록 저장

선택 이유까지 고른 뒤 `saveEpisodeProgress()`가 `user_episode_progress`에 현재 상태를 `upsert`한다.

`upsert`는 다음 뜻이다.

- 같은 사용자·같은 에피소드 기록이 없으면 새로 추가
- 이미 있으면 그 행을 수정

저장 항목:

- 현재 장면
- 원칙별 점수
- 전체 선택 기록
- 판단 이유
- 응답 시간
- 사전·사후 응답
- 완료 여부
- 엔딩
- 수정 시각

`unique(user_id, episode_id)` 제약 때문에 한 사용자는 에피소드마다 한 개의 최신 진행 행을 가진다.

## 4.9 결과 리포트

에피소드가 끝나면 다음을 보여준다.

- Good / Normal / Bad End
- 전체 수행 점수
- 7대 원칙 중 이번 에피소드에서 평가한 원칙별 점수
- 강한 선택과 점검할 선택
- 정책 근거 코드
- 사전·사후 생각 변화
- 위험 선택 비율과 적극 실천 비율
- 학습자 유형
- 취약 원칙
- 다음 행동과 에피소드 추천
- AI에게 결과 설명 질문
- 관련 학습 영상

# 5. 스토리 엔진

## 5.1 에피소드는 어떻게 표현되는가

`js/app.js`의 `episodes` 배열에 5개 에피소드가 데이터로 정의되어 있다.

1. 삭제되지 않은 얼굴: 딥페이크·초상권
2. 진실은 클릭 뒤에 있다: AI 허위정보·검증
3. AI 챗봇과 마음의 거리: 의존·정신건강
4. AI가 써준 수행평가: 과제·표절·투명성
5. 추천 알고리즘이 아는 것: 개인정보·공정성

각 에피소드는 다음 정보를 가진다.

```text
에피소드 ID
제목과 요약
평가할 윤리원칙 목록
시작 장면 ID
사전·사후 질문
장면들의 모음
```

각 장면은 다음 정보를 가진다.

```text
장면 제목
상황 설명
친구의 말
선택지 목록
각 선택 뒤 이동할 다음 장면
피드백
```

즉, 장면이 노드이고 선택지가 화살표인 그래프 구조다. 선택에 따라 다른 장면으로 이동하므로 단순한 순서형 퀴즈보다 분기형 스토리에 가깝다.

## 5.2 왜 콘텐츠와 화면을 분리했는가

화면 코드를 매번 새로 만들지 않고 에피소드 데이터만 바꾸면 같은 엔진이 다른 이야기를 실행할 수 있다.

이 설계의 장점:

- 에피소드 추가가 쉬움
- 모든 에피소드 UI가 일관됨
- 저장 형식이 같음
- 테스트에서 모든 장면과 선택지를 한 번에 검사 가능

현재 자동 테스트 기준으로 22개 판단 장면, 61개 선택지, 7개 윤리원칙을 검사한다.

# 6. 점수 계산을 숫자로 이해하기

## 6.1 왜 기존의 `+10`, `-5` 방식을 버렸는가

단순 가감점은 “왜 이 선택은 10점이고 다른 선택은 15점인가?”라는 질문에 정책적 근거를 설명하기 어렵다.

현재는 각 선택을 관련 원칙마다 0~4 행동 수준으로 따로 평가한다. 따라서 같은 선택도 프라이버시는 4, 투명성은 2가 될 수 있다.

## 6.2 원칙별 점수 공식

```text
원칙별 점수
= 획득한 행동 단계 합계 ÷ 가능한 최대 단계 합계 × 100

가능한 최대 단계 합계
= 그 원칙이 평가된 선택 수 × 4
```

예를 들어 프라이버시가 세 번 평가되었고 단계가 `4, 3, 1`이면:

```text
획득 = 4 + 3 + 1 = 8
최대 = 3 × 4 = 12
프라이버시 점수 = 8 ÷ 12 × 100 = 66.7 → 67점
```

책임성이 두 번 평가되어 `4, 3`이면:

```text
획득 = 7
최대 = 8
책임성 점수 = 7 ÷ 8 × 100 = 87.5 → 88점
```

## 6.3 전체 점수

이번 에피소드에서 실제로 평가된 원칙별 점수의 산술평균이다.

```text
프라이버시 67, 책임성 88, 안전성 75, 투명성 50
전체 = (67 + 88 + 75 + 50) ÷ 4 = 70점
```

평가되지 않은 원칙은 0점으로 넣지 않는다. 평가하지 않은 것을 실패로 취급하면 점수가 왜곡되기 때문이다.

## 6.4 엔딩 기준

- 75~100: Good End
- 50~74: Normal End
- 0~49: Bad End

이 기준은 정부 공식 등급이 아니다. 교육용 피드백을 위해 팀이 정의한 내부 구간이다.

## 6.5 정책 근거

최상위 평가 축은 `대한민국 인공지능 윤리원칙`의 7대 원칙이다.

1. 인간중심성
2. 프라이버시 보호
3. 공정성·포용성
4. 책임성
5. 안전성
6. 신뢰성
7. 투명성

법률은 학생 선택을 법 위반이라고 판정하는 점수표로 사용하지 않는다. 관련 맥락을 알려주는 참고 태그로만 사용한다.

# 7. 직접 만든 분석 엔진

분석 엔진을 여러 파일로 나눈 이유는 한 파일이 모든 일을 하면 수정과 검증이 어려워지기 때문이다. 각 파일은 한 가지 책임만 가진다.

## 7.1 `principle-scorer.js`: 원칙 점수 계산기

입력:

- 선택별 0~4 루브릭
- 정책 근거 코드
- 에피소드 선택 기록

처리:

- 유효한 0~4 값만 사용
- 원칙별 획득 단계와 최대 단계 합산
- 0~100으로 정규화
- 근거 코드와 법률 참고를 중복 없이 모음

출력:

- 원칙 이름
- 점수
- 평가 선택 수
- 획득 단계와 최대 단계
- 정책 근거

## 7.2 `feature-extractor.js`: 행동 기록을 숫자로 바꾸는 모듈

원시 선택 기록은 그대로는 분석하기 어렵다. 특징 추출은 긴 기록을 비교 가능한 숫자로 요약한다.

추출 특징:

- 선택 수
- 전체 점수
- 위험 선택 수와 비율: 단계 0~1
- 적극 실천 수와 비율: 단계 3~4
- 판단 이유 응답률
- 판단 이유 분포
- 가장 많이 선택한 판단 이유
- 평균 응답 시간
- 사후 단계 - 사전 단계
- 시도 횟수
- 원칙별 점수
- 가장 약한 원칙과 강한 원칙
- 원칙 점수 차이

이렇게 만들어진 숫자 묶음을 `feature vector`, 즉 특징 벡터라고 부른다.

## 7.3 `learner-classifier.js`: 설명 가능한 유형 분류

이 파일은 머신러닝이 아니라 `if` 조건으로 만든 규칙 기반 분류기다.

주요 규칙:

1. 선택 기록이 없으면 `분석 대기`
2. 위험 선택 비율이 40% 이상이면 `위험 신호 점검형`
3. 전체 75점 이상, 위험 선택 25% 이하, 원칙 편차 35점 이하이면 `균형 실천형`
4. 그 외에는 가장 낮은 원칙의 그룹에 따라 유형 결정

취약 원칙 그룹:

- 인간중심성 → AI 의존 점검형
- 프라이버시·공정성 → 권리 보호 점검형
- 책임성·안전성 → 책임 행동 보완형
- 신뢰성·투명성 → 검증 강화형

교수님이 “왜 이런 유형이 나왔나요?”라고 물으면 분류 규칙을 그대로 보여줄 수 있다. 이것이 설명 가능성이다.

## 7.4 데이터 충분도

분석 결과를 너무 확신하지 않도록 데이터 충분도를 따로 계산한다.

```text
선택 수: 최대 50점
판단 이유 응답률: 최대 25점
사전·사후 응답 존재: 15점
2회 이상 반복: 10점
```

- 75 이상: 높음
- 45 이상: 보통
- 그 미만: 낮음

이 수치는 심리검사의 신뢰도 계수가 아니라, 현재 분석에 사용된 행동 기록이 얼마나 갖추어졌는지 나타내는 내부 지표다.

## 7.5 `content-recommender.js`: 다음 학습 추천

가장 낮은 원칙을 기준으로 다음 행동과 에피소드를 추천한다.

예:

```text
취약 원칙: 프라이버시
추천 행동: 사용 전 당사자의 동의와 공개 범위를 확인하기
추천 에피소드: 추천 알고리즘이 아는 것
```

이미 완료한 에피소드라면 `다음 학습` 대신 `복습`으로 표시할 수 있다.

## 7.6 `js/analysis/learning-model.js`: 통합 조정자

앞의 모듈을 순서대로 호출한다.

```text
특징 추출
→ 유형 분류
→ 데이터 충분도 계산
→ 콘텐츠 추천
→ 분석 추적 문장 생성
```

출력에 모델 버전과 하위 모듈 버전을 함께 기록한다. 나중에 규칙이 바뀌었을 때 어떤 버전으로 분석했는지 구분하기 위해서다.

## 7.7 `teaching-strategy.js`: 교수자 지도 활동 추천

교수자 대시보드에서 가장 취약한 원칙에 맞는 수업 활동과 관찰 기준을 제안한다.

예:

- 프라이버시 취약: 동의를 받을 대상과 공개 범위를 정하는 역할극
- 신뢰성 취약: AI 답과 원문·다른 출처 비교
- 책임성 취약: 신고, 수정, 피해 회복, 재발 방지 순서 설계

## 7.8 `js/scoring-engine.js`: 호환 어댑터

예전 코드가 하나의 점수 엔진을 호출하던 방식을 깨지 않으면서, 내부적으로 새 모듈을 사용하도록 연결한다. 이런 파일을 어댑터라고 한다.

# 8. OpenAI 기능

## 8.1 OpenAI가 하는 일

OpenAI는 두 가지 보조 기능에만 사용한다.

1. 장면별 판단 이유 후보 3개 생성
2. 이미 계산된 결과를 학생 눈높이로 설명

OpenAI가 하지 않는 일:

- 윤리 점수 결정
- Good/Normal/Bad 엔딩 결정
- 공식 법률 판정
- 회원 인증
- DB 저장
- 교수자 통계 계산

## 8.2 왜 브라우저에서 직접 호출하지 않는가

브라우저 코드에 OpenAI API 키를 넣으면 누구나 개발자 도구에서 볼 수 있다. 그래서 `/api/explain-result.js`라는 Vercel 서버 함수를 통과한다.

## 8.3 서버 함수의 방어 단계

1. POST 요청인지 확인
2. Supabase 로그인 토큰 검증
3. 문자열 길이와 숫자 범위 제한
4. 필요한 데이터가 있는지 확인
5. OpenAI에 엄격한 JSON Schema로 응답 요청
6. 응답 구조 재검증
7. 실패 시 재시도 또는 로컬 설명 사용
8. `Cache-Control: no-store`로 민감한 결과 캐시 방지

## 8.4 결과 설명 실패 대비

OpenAI 응답이 비어 있거나 형식이 틀리면 더 큰 출력 한도로 한 번 재시도한다. 그래도 실패하면 가장 강한 원칙과 가장 약한 원칙을 이용해 서버 안의 `buildFallbackExplanation()`이 설명을 만든다.

따라서 OpenAI가 잠시 불안정해도 핵심 학습과 점수 계산은 계속 작동한다.

## 8.5 YouTube 추천

OpenAI가 학습 검색어를 만들고, YouTube API가 한국어 영상 최대 3개를 찾는다.

- YouTube 키가 있으면 영상 카드 반환
- 키가 없거나 검색 실패면 YouTube 검색 링크 제공
- 검색 결과는 서버 메모리에 잠시 캐시

영상 내용 전체를 시스템이 검증한 것은 아니므로 추천 학습 자료이며 공식 검증 자료라고 말하면 안 된다.

# 9. Supabase 백엔드와 보안

## 9.1 왜 Supabase를 사용했는가

직접 서버, 인증, DB, 비밀번호 보안을 처음부터 만들기보다 다음 기능을 안정적으로 결합할 수 있기 때문이다.

- 인증
- PostgreSQL
- 자동 Data API
- RLS
- SQL 함수 RPC

## 9.2 공개 가능한 anon key와 비밀 키의 차이

`js/config/supabase-config.js`의 anon key는 브라우저용 공개 키다. 이 키만으로 모든 데이터를 볼 수 없어야 하고, 실제 보호는 RLS가 한다.

반대로 OpenAI API 키와 YouTube API 키는 비용과 권한이 연결된 비밀 키이므로 Vercel 환경변수에만 둔다.

## 9.3 RLS

RLS는 Row Level Security의 약자다. 같은 표 안에서도 사용자가 볼 수 있는 행을 제한한다.

`profiles` 정책:

- 로그인한 사용자는 자기 ID와 같은 프로필만 조회·수정 가능

`user_episode_progress` 정책:

- 로그인한 사용자는 `auth.uid() = user_id`인 자기 기록만 조회·추가·수정 가능

즉, 브라우저에서 다른 사용자 ID로 조회를 시도해도 DB가 막는다.

## 9.4 교수자 권한

누구나 교수자 화면을 보는 것이 아니다.

1. 관리자가 SQL로 신뢰할 계정을 `teacher_accounts`에 등록
2. 브라우저가 `get_teacher_dashboard()` RPC 호출
3. SQL 함수가 현재 로그인 ID가 교수자인지 확인
4. 아니면 오류 코드 `42501`
5. 교수자이면 익명 집계 JSON만 반환

`teacher_accounts` 표 자체는 일반 사용자에게 읽기 권한을 주지 않는다.

## 9.5 왜 교수자 집계를 SQL 함수에서 하는가

모든 학생의 원본 기록을 브라우저로 내려보낸 뒤 JavaScript로 집계하면 개인정보 노출 위험이 크다.

현재는 DB 서버 안에서 통계만 계산하여 다음 값만 보낸다.

- 참여자 수
- 에피소드 완료율
- 평균 사전·사후 변화
- 문항별 위험 선택 비율
- 원칙별 평균
- 동의 인원과 적격 기록 수

학생 이름, 아이디, 이메일, 개인 답변은 교수자 대시보드 응답에 포함하지 않는다.

# 11. K-means 군집분석

## 11.1 왜 Decision Tree 대신 K-means인가

Decision Tree와 Logistic Regression은 보통 정답 라벨이 필요하다.

예:

```text
이 학생은 A유형이다
이 학생은 B유형이다
```

현재는 전문가가 붙인 정답 유형 라벨이 없다. 없는 정답을 가짜로 만들면 모델 정확도도 의미가 없다.

K-means는 정답 라벨 없이 특징이 비슷한 데이터를 묶는 비지도학습이므로 현재 목적에 더 맞다.

## 11.2 입력 특징

- 7대 원칙 점수
- 평균 응답 시간
- 사전·사후 변화
- 위험 선택 비율
- 적극 실천 비율
- 가장 많이 선택한 판단 이유

## 11.3 전처리

숫자형 데이터:

1. 빠진 값은 중앙값으로 채움
2. `StandardScaler`로 단위를 맞춤

범주형 데이터:

1. 빠진 값은 가장 자주 나온 값으로 채움
2. 판단 이유를 `OneHotEncoder`로 숫자 열로 변환

응답 시간은 초 단위이고 점수는 0~100이므로 그대로 비교하면 점수 범위가 더 큰 영향을 줄 수 있다. 표준화는 이런 단위 차이를 줄인다.

## 11.4 군집 수 선택

2~5개 후보를 시험하고 실루엣 점수가 가장 높은 군집 수를 선택한다.

실루엣 점수는 같은 군집끼리는 가깝고 다른 군집과는 멀리 떨어져 있는지를 보는 지표다. 일반적으로 높을수록 분리가 비교적 잘 된 것이다.

## 11.5 출력

- 각 기록의 군집 번호 CSV
- 군집별 요약 JSON
- 전처리기와 K-means 모델 `joblib`
- 군집별 취약 원칙
- 평균 위험률
- 평균 생각 변화
- 맞춤 지도 활동

## 11.6 현재 한계

- 아직 50건 기준을 충족하지 않아 실제 연구 결과를 제시하지 않음
- 50건은 파일럿 실행을 위한 최소 내부 기준이지 통계적 충분성을 보장하지 않음
- 현재 준비도 화면은 적격 학습 기록 수를 집계함
- 학습자 유형을 연구하려면 최종적으로 사용자별 여러 에피소드를 한 행으로 집계하는 방식이 더 적절함
- 군집 번호 자체에는 좋고 나쁨의 의미가 없음
- 실제 교육 효과 주장은 별도의 사용자 연구와 통계 검증이 필요함

정확한 발표 표현:

> K-means 파이프라인은 구현했지만 현재는 데이터 수집 단계이므로 실제 군집 결과를 연구 성과처럼 제시하지 않습니다. 동의한 실제 데이터가 기준을 충족한 뒤 탐색적으로 사용합니다.

> Supabase의 이메일·비밀번호 인증 방식을 아이디 로그인 UI에 맞게 사용하기 위해 아이디를 고정 도메인의 내부 인증 문자열로 변환합니다. 실제 메일 주소가 아니므로 이메일 인증과 비밀번호 찾기는 현재 지원하지 않는 한계가 있습니다.

> 현재 운영 모델은 정책 기반 설명 가능 분석 모델입니다. 원칙 점수 계산, 특징 추출, 유형 분류, 추천을 독립 모듈로 직접 구현했습니다. 생성형 AI API 자체를 저희 모델이라고 부르지는 않습니다. K-means는 실제 데이터 수집 후 집단 패턴을 탐색하기 위한 별도 파일럿입니다.

**Q. 왜 딥러닝을 쓰지 않았나요?**

> 현재는 학습시킬 충분한 실제 데이터와 전문가 정답 라벨이 없습니다. 이 상황에서 딥러닝이나 분류 정확도를 제시하면 근거가 약해집니다. 교육 피드백은 근거를 설명할 수 있는 규칙 기반으로 제공하고, 라벨이 필요 없는 K-means를 후속 탐색에 사용하도록 설계했습니다.

**Q. OpenAI가 점수를 만들면 매번 결과가 달라지지 않나요?**

> OpenAI는 점수에 관여하지 않습니다. 점수는 저장된 0~4 루브릭을 JavaScript 계산식으로 처리하므로 같은 선택이면 같은 점수입니다. OpenAI는 이미 나온 결과를 자연어로 설명합니다.

**Q. 모델 정확도와 F1은 얼마인가요?**

> 현재 운영 모델은 정답 라벨을 예측하는 통계 분류 모델이 아니므로 accuracy와 F1을 제시하는 대상이 아닙니다. 규칙의 정확성은 단위 테스트와 전체 분기 테스트로 검증합니다. K-means도 비지도학습이라 accuracy와 F1 대신 실루엣 점수와 군집 안정성, 교육적 해석 가능성을 검토합니다.

# 16. 세 파트가 겹치는 지점

실제 프로젝트는 완전히 세 조각으로 분리되지 않는다. 아래 인터페이스는 세 명 모두 이해해야 한다.

```text
프론트가 saveEpisodeProgress() 호출
→ Supabase Data API
→ RLS가 사용자 ID 검사
→ DB에 upsert
```

## 프론트 ↔ 분석

```text
학생 선택
→ history에 rubric과 reason 저장
→ principle scorer
→ feature extractor
→ classifier/recommender
→ 결과 UI
```

## 백엔드 ↔ AI

```text
프론트가 로그인 토큰과 결과 전송
→ Vercel 서버가 Supabase로 토큰 검증
→ OpenAI 호출
→ 검증된 JSON 응답 반환
```

각 담당자는 자기 파트뿐 아니라 이 경계 흐름을 한 번은 직접 설명해야 한다.

# 17. 교수님 공통 질문과 답변

## Q1. 웹페이지에 정해진 콘텐츠를 넣고 클릭하면 점수가 바뀌는 것 외에 핵심 개발이 무엇인가요?

> 사용자의 선택을 단순 가감점으로 처리하지 않고, 선택별 다차원 윤리 루브릭과 판단 이유, 응답 시간, 사전·사후 변화를 구조화했습니다. 이를 원칙 점수 계산, 특징 추출, 유형 분류, 콘텐츠 추천 모듈로 나눈 분석 파이프라인을 구현했습니다. 또한 학생용 개인 피드백과 교수자용 익명 집계를 서로 다른 보안 경로로 제공하고, AI 설명 장애 시에도 핵심 기능이 유지되도록 fallback을 구현했습니다.

## Q2. 사용 기술은 무엇인가요?

> 프론트엔드는 HTML5, CSS3, Vanilla JavaScript이고, 백엔드는 Supabase Auth와 PostgreSQL, RLS, SQL RPC, Vercel Node.js Serverless Function을 사용했습니다. AI 보조는 OpenAI Responses API, 영상 추천은 YouTube Data API를 사용합니다. 자체 분석은 JavaScript 모듈로 구현했고, 파일럿 군집분석은 Python, pandas, scikit-learn의 K-means를 사용합니다. 코드는 GitHub에서 관리하고 Vercel로 배포합니다.

## Q3. 왜 이 점수가 공신력이 있다고 볼 수 있나요?

> 공식 인증 점수라고 주장하지 않습니다. 평가 축은 대한민국 인공지능 윤리원칙을 사용했고, 행동 수준 0~4는 이를 교육 장면에 적용하기 위해 팀이 조작적으로 정의한 루브릭입니다. 계산 과정과 근거 코드를 공개해 설명 가능하게 만들었지만, 전문가 내용타당도와 사용자 연구는 이후 검증 과제로 명시했습니다.

## Q4. 교육 효과를 어떻게 검증할 건가요?

> 현재는 에피소드별 사전·사후 판단 수준 변화를 수집합니다. 본 검증에서는 동일 학습자의 전후 변화, 완료율, 위험 선택 비율 변화를 보고, 표본이 충분하면 대응표본 검정과 효과크기를 사용할 계획입니다. 현재 수치만으로 교육 효과를 확정하지 않습니다.

## Q5. 개인정보는 어떻게 보호하나요?

> 비밀번호는 Supabase Auth가 관리하고 앱 DB에 저장하지 않습니다. RLS로 개인 기록을 본인에게만 허용하고, 교수자 화면은 권한 있는 계정에 익명 집계만 반환합니다. OpenAI 요청에는 이름과 아이디, 비밀번호를 보내지 않고 에피소드 결과와 선택 정보만 보냅니다. 연구 활용 데이터는 별도 동의를 받습니다.

## Q6. 생성형 AI가 틀린 답을 주면 어떻게 하나요?

> AI는 핵심 점수와 엔딩을 결정하지 않습니다. 출력은 JSON Schema와 허용 코드, 길이, 말투로 검증합니다. 실패 시 재시도하거나 로컬 fallback을 사용하므로 스토리 진행과 점수 계산은 중단되지 않습니다.

## Q7. 왜 자체 서버를 만들지 않았나요?

> 프로젝트 범위에서 인증과 DB 보안을 직접 재구현하는 대신 Supabase의 관리형 Auth와 PostgreSQL을 사용했습니다. 대신 데이터 모델, RLS 정책, RPC 집계 함수, 진행 저장 로직, Vercel 서버 인증과 AI API 연결은 직접 설계하고 구현했습니다.

## Q8. 한 명이 50번 하면 K-means 기준을 충족하나요?

> 현재 UI는 적격 기록 수를 보여주지만 학습자 집단 분석의 연구 설계에서는 서로 다른 학습자 단위가 중요합니다. 한 사람의 반복은 개인 내 신뢰도를 높일 수는 있어도 50명의 다양성을 대신하지 못합니다. 실제 분석 전에는 사용자별 에피소드를 집계한 학습자 단위 데이터셋으로 정리해야 합니다.

## Q9. 합성 데이터 120명은 학습에 썼나요?

> 사용하지 않았습니다. 화면 시연을 위해 브라우저에서 고정 난수로 생성하며 실제 DB, 동의 수, K-means 입력과 분리되어 있습니다.

## Q10. 가장 큰 한계는 무엇인가요?

> 루브릭의 전문가 타당도 검토와 실제 학습자 표본이 부족합니다. 따라서 현재는 설명 가능한 교육 프로토타입과 데이터 수집 시스템의 완성을 주장하고, 표준화된 윤리 검사나 검증 완료된 예측 모델이라고 주장하지 않습니다.

# 18. 절대 하면 안 되는 답변

## 나쁜 답변 1

> AI가 알아서 점수를 냅니다.

왜 문제인가: 사실과 다르며 재현성과 설명 가능성이 사라진다.

바른 답변:

> 점수는 팀이 구현한 정책 기반 규칙 엔진이 계산하고, OpenAI는 결과를 쉬운 말로 설명합니다.

## 나쁜 답변 2

> 저희가 AI 모델을 학습했습니다.

왜 문제인가: 현재 실제 학습 완료 모델이 없다.

바른 답변:

> 현재 운영은 규칙 기반 모델이고, 실제 데이터가 모이면 실행할 K-means 군집분석 파이프라인을 구현했습니다.

## 나쁜 답변 3

> 50건이면 정확합니다.

왜 문제인가: 50은 파일럿 실행 기준이지 정확도 보장이 아니다.

바른 답변:

> 50건은 너무 작은 표본에서 무리하게 분석하지 않도록 둔 최소 파일럿 기준이며, 결과의 안정성은 별도로 검토해야 합니다.

## 나쁜 답변 4

> 정부가 정한 점수입니다.

왜 문제인가: 정부는 0~4 배점과 엔딩 기준을 정하지 않았다.

바른 답변:

> 원칙은 국가 자료에 근거하고, 행동 루브릭과 점수 구간은 교육 적용을 위해 팀이 조작화한 기준입니다.

## 나쁜 답변 5

> 각자 맡은 부분이라 다른 코드는 모릅니다.

왜 문제인가: 시스템 통합 이해가 없다는 인상을 준다.

바른 답변:

> 제 주 담당은 이 부분이고, 다른 파트와는 이 API와 데이터 형식으로 연결됩니다.

# 20. 팀 전체가 외울 최종 답변

> 저희는 처음에는 선택형 콘텐츠 중심이어서 개발 깊이가 부족하다는 피드백을 받았습니다. 재설계 후에는 선택을 단순 점수가 아니라 원칙별 행동 수준, 판단 이유, 응답 시간, 사전·사후 변화로 구조화했습니다. 이를 점수 계산, 특징 추출, 설명 가능한 유형 분류, 추천 모듈로 분리했고, 학생 리포트와 교수자 익명 대시보드까지 연결했습니다. 인증과 저장은 Supabase의 RLS로 보호하고, OpenAI는 점수가 아니라 설명과 문항 보조에만 사용합니다. 실제 데이터가 충분해진 뒤 사용할 K-means 군집분석 파이프라인도 구현했지만, 현재 데이터가 부족하므로 검증된 연구 결과라고 과장하지 않습니다.

이 답변 뒤에는 각 담당자가 자기 파일을 열어 입력, 처리, 출력, 오류 대응을 설명할 수 있어야 한다.
